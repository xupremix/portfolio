**As a** recruiter or hiring manager evaluating Filippo, **I want to** land on a visually coherent,
on-brand site shell — with a consistent nav and footer — before any page content has been added,

defined) — this plan produces the literal reusable design-system tokens; the next plan in this phase
(01-02) makes them visible in a browser via the nav/footer shell.

Output: a buildable Astro project at the repo root with `npm run build` producing Tailwind-styled
static output, and a `src/styles/global.css` `@theme static` block containing every color/spacing/
typography/font token from UI-SPEC.md.

<task type="auto">
  <name>Task 1: Scaffold Astro project into the repo root</name>
  <files>package.json, package-lock.json, astro.config.mjs, tsconfig.json, .gitignore, .vscode/extensions.json, .vscode/launch.json, public/favicon.svg, public/favicon.ico, src/pages/index.astro</files>
  <action>
Run `npm create astro@latest .astro-scaffold-tmp -- --template minimal --no-git --install --yes --skip-houston --no-ai` from the repo root. Scaffold into this explicit, throwaway subdirectory rather than `.` directly: `create-astro` detects that the repo root already contains `.git`, `.claude`, and `.planning`, and when targeted at `.` it silently redirects the scaffold into an auto-generated subdirectory instead of the current directory — confirmed empirically during planning. An explicit named target directory is the only reliable way to control where the output lands. `--no-git` skips re-initializing git (this repo already has commit history). `--no-ai` skips Astro's generated `AGENTS.md`/`CLAUDE.md` files so they don't collide with or duplicate the project's real `.claude/CLAUDE.md`. `--install` runs `npm install` as part of scaffolding.

Once scaffolding finishes, merge the temp directory's contents — including dotfiles — into the repo root with `cp -a .astro-scaffold-tmp/. .`, then remove the temp directory with `rm -rf .astro-scaffold-tmp`. The trailing `/.` on the source path is required so hidden entries like `.gitignore` and `.vscode/` are included in the copy; a bare glob (`.astro-scaffold-tmp/*`) would silently skip them.

After merging, confirm the repo root has: `package.json` with `dev`/`build`/`preview` npm scripts, `astro.config.mjs`, `tsconfig.json` (extends `astro/tsconfigs/strict`), `src/pages/index.astro` (Astro's default starter markup — this is fully replaced with the real homepage in this phase's next plan, not shipped as final content), and `public/favicon.svg` + `public/favicon.ico`.
  </action>
  <verify>
    <automated>test -f package.json && test -f astro.config.mjs && test -f src/pages/index.astro && npm run build && test -f dist/index.html</automated>
  </verify>
  <done>Astro project is scaffolded at the repo root (not a subdirectory); .astro-scaffold-tmp no longer exists; npm run build exits 0 and produces dist/index.html.</done>
</task>

<task type="auto">
  <name>Task 2: Add Tailwind v4, self-hosted fonts, and icon tooling</name>
  <files>package.json, package-lock.json, astro.config.mjs, src/styles/global.css</files>
  <action>
Run `npx astro add tailwind --yes`. This is Astro's official Tailwind v4 setup path (confirmed against Astro's own docs during planning): it installs `@tailwindcss/vite` + `tailwindcss`, creates `src/styles/global.css` containing `@import "tailwindcss";`, and adds a `vite: { plugins: [tailwindcss()] }` block to `astro.config.mjs`. Do not install the older `@astrojs/tailwind` integration package — that targets Tailwind v3's PostCSS pipeline and is unrelated to what `astro add tailwind` installs on this Astro version.

Then install the remaining Phase 1 dependencies in one command: `npm install @fontsource/inter @fontsource/jetbrains-mono astro-icon @iconify-json/lucide`. Do not run `npx astro add astro-icon` — that command fails in this environment (confirmed during planning: it errors trying to fetch third-party integration catalog metadata over the network). `astro-icon` must be installed as a plain npm dependency and wired manually instead.

Manually edit `astro.config.mjs`: add `import icon from 'astro-icon';` alongside the existing `@tailwindcss/vite` import, and add an `integrations: [icon()]` entry to the `defineConfig({...})` call so it sits next to the existing `vite: { plugins: [tailwindcss()] }` key — both are independent, unrelated config entries that coexist in the same object. `@iconify-json/lucide` needs no config of its own: astro-icon auto-discovers installed `@iconify-json/*` packages and exposes their icons through `<Icon name="lucide:icon-name" />` from `astro-icon/components` (verified during planning with a real build using `lucide:menu` and `lucide:github`, both rendered as inlined `<svg>` elements in the build output).
  </action>
  <verify>
    <automated>grep -c "astro-icon" astro.config.mjs && grep -c "tailwindcss" astro.config.mjs && grep -cE '"@fontsource/inter"|"@fontsource/jetbrains-mono"|"astro-icon"|"@iconify-json/lucide"' package.json && npm run build</automated>
  </verify>
  <done>astro.config.mjs registers both the Tailwind v4 vite plugin and the astro-icon integration; package.json lists all four newly added dependencies; npm run build still exits 0.</done>
</task>

<task type="auto">
  <name>Task 3: Encode the UI-SPEC design-system tokens as a Tailwind v4 @theme block</name>
  <files>src/styles/global.css</files>
  <action>
Replace the contents of `src/styles/global.css` with `@import "tailwindcss";` followed by a
`@theme static { ... }` block. Use the `static` keyword, not plain `@theme` — `static` forces every
declared custom property into the compiled `:root,:host` output regardless of whether any utility
class using it appears yet in scanned markup. Without `static`, Tailwind v4 prunes theme variables
that no page currently references, which would make this token layer invisible in the build until
Nav/Footer/Layout exist in this phase's next plan (confirmed via a real build comparison during
planning: an identical token block without `static` emitted only the subset of tokens actually used
by classes present in scanned source, silently dropping the rest).

Declare exactly these custom properties inside the `@theme static` block, with values taken verbatim
from UI-SPEC.md's Color, Spacing, and Typography tables:

Colors: color-base #1E1E2E, color-mantle #181825, color-accent #CBA6F7, color-destructive #F38BA8,
color-text #CDD6F4, color-subtext #A6ADC8, color-border #313244 (each declared as a `--color-*`
custom property).

Spacing: spacing-xs 4px, spacing-sm 8px, spacing-md 16px, spacing-lg 24px, spacing-xl 32px,
spacing-2xl 48px, spacing-3xl 64px (each declared as a `--spacing-*` custom property).

Fonts: font-sans set to "Inter", ui-sans-serif, system-ui, sans-serif; font-mono set to
"JetBrains Mono", ui-monospace, monospace (each declared as a `--font-*` custom property).

Typography (Tailwind v4's paired size + line-height key syntax: `--text-{name}` plus the companion
`--text-{name}--line-height`): text-body 16px / line-height 1.5, text-label 14px / line-height 1.4,
text-heading 28px / line-height 1.2, text-display 48px / line-height 1.1.

That is 7 color + 7 spacing + 2 font + 8 typography (4 sizes x 2 keys each) = 24 custom properties
total. Do not add a color alias for the "Secondary pastel set" tag colors (Teal/Sky/Peach/Green) —
those belong to Phase 3's tech-stack badges per UI-SPEC and are explicitly out of this phase's
Component Inventory. This `@theme static` block is the literal "design system defined" deliverable
for SETUP-02: every later phase's color/spacing/typography classes must derive from these tokens
(for example `bg-base`, `text-accent`, `p-lg`, `text-heading`), not new arbitrary hex/px values.
  </action>
  <verify>
    <automated>npm run build && find dist -name '*.css' -exec cat {} + | grep -oE -- '--(color-base|color-mantle|color-accent|color-destructive|color-text|color-subtext|color-border|spacing-xs|spacing-sm|spacing-md|spacing-lg|spacing-xl|spacing-2xl|spacing-3xl|font-sans|font-mono|text-body|text-body--line-height|text-label|text-label--line-height|text-heading|text-heading--line-height|text-display|text-display--line-height):' | sort -u | wc -l</automated>
  </verify>
  <done>Build succeeds; the verify command's grep pipeline outputs 24 — all 24 declared design tokens (7 colors + 7 spacing values + 2 font families + 8 typography size/line-height pairs) are present in the compiled CSS's root theme layer.</done>
</task>
